# gm-database-schema-gkt.1 — retained evidence

Everything the spike document quotes, kept so its tables can be audited rather
than believed. gm-database-schema-9c8.3's reviewer could not check its sibling's
Neo4j access counts because the captures had been discarded; nothing here is
discarded.

## Layout

One directory per (scale × mode), each holding the same five things.

| Directory | Scale | Mode | Machine |
| --- | --- | --- | --- |
| `small-local/` | fixture, 5,000 releases | local Docker | Docker Desktop VM, Apple M1 Pro, 2 vCPU |
| `large-local/` | synthetic, 1,000,000 releases | local Docker | the same |
| `small-cloud/` | fixture | IBM Cloud | VPC `bx2-8x32`, `us-south-1`, 8 vCPU |
| `large-cloud/` | synthetic | IBM Cloud | the same |
| `large-local-cap-cost/` | synthetic | local Docker | the depth-cap sweep on a connected pair |

| File | What it is |
| --- | --- |
| `postgres-<scale>-<mode>.json` | Every iteration of every PostgreSQL workload: p50, p95, min, max, mean, stdev, the raw `samples_ms`, the answer, the work counters, and the buffer totals. |
| `neo4j-<scale>-<mode>.json` | The same for Neo4j, with `PROFILE` database accesses in place of buffers. |
| `report.md` | The tables the spike document carries, generated by `../bench/report.py`. |
| `verdict.json` | The bead's gate evaluated by `../bench/compare.py`: answer agreement, worst p95 per variant, and the measured ceiling when it fails. |
| `plans/` | One capture per headline workload. `EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` for PostgreSQL, Cypher `PROFILE` for Neo4j. |
| `calibration-*.json` | What the machine could do, measured by `../bench/calibration.py` on the machine itself. |
| `neo4j-import-*.txt`, `neo4j-stats-*.txt` | The bulk import and the node and relationship counts it produced, so both engines can be shown to hold the same graph. |
| `hub-expansion.txt` | One Genre vertex scanned, then scanned and inserted, three times each under `EXPLAIN (ANALYZE, BUFFERS)`. The evidence for the claim that a single hub write is the whole remaining gap. |
| `coverage.txt` | An exhaustive breadth-first search out of the seed artist. The evidence that the catalog's eccentricity is 4, which the depth-cap recommendation rests on. |
| `explore-row-limit.txt` | `pf.explore` with and without its row limit, in one capture. The single most load-bearing control in the document. |

## Reading the JSON

```bash
# The p95 of every workload the Verdict gate reads.
jq -r '.results[] | select(.verdict_gate) | [.workload, .p95_ms] | @tsv' large-local/postgres-large-local.json

# Whether PostgreSQL and Neo4j agreed, and where they did not.
jq '{answers_match, disagreements, measured_ceiling, go}' large-local/verdict.json

# What a search actually did, as opposed to how long it took.
jq -r '.results[] | select(.variant=="pf-vaat" and .depth==10)
       | [.case, .answer.work.expanded, .answer.work.seen_rows, .accesses.total_accesses] | @tsv' \
   large-local/postgres-large-local.json
```

## The three captures that are not benchmark output

`hub-expansion.txt`, `coverage.txt` and `explore-row-limit.txt` come from
`../hub-cost.sh` rather than from `../bench/runner.py`, because each answers a
question about a single statement rather than about a workload's distribution.
All three were originally run at a psql prompt and quoted from the terminal,
which is the habit gm-database-schema-9c8.3 was bounced for; they are a committed
script with committed output now, and every figure the document draws from them
is a median of three repetitions rather than one sample.

## Two things a reader should check first

**The answers.** Every `verdict.json` reports `"answers_match": true`. That is
the claim the timings hang on, and it compares path DISTANCES rather than paths
(`shortestPath` breaks ties arbitrarily) and explore discovery sets with the row
limit removed on both engines (`ORDER BY dist LIMIT 100` over a band of several
hundred returns an arbitrary hundred either side). `../bench/compare.py` states
both rules in code.

**The machines.** `calibration-local.json` and `calibration-cloud.json` are why
the cloud numbers are worse than the laptop's despite four times the cores: one
core of a `bx2-8x32` is about 4.5 times slower than one core of an M1 Pro at this
work, and its disk writes at a tenth of the rate. Nothing in the document is
rescaled to hide that.
